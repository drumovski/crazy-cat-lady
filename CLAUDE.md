# Crazy Cat Lady

A reskin of the kids' card game Sleeping Queens, renamed to avoid copyright issues. Card mapping:

| Sleeping Queens | Crazy Cat Lady | Effect |
|---|---|---|
| Queens | Cats | Collected; the win condition |
| Kings | Dogs | Wake a sleeping cat |
| Knights | Fish | Steal an awake cat from another player |
| Dragons | Seagulls | Block/counter a Fish steal ("they eat the fish") |
| Sleeping Potion | Catnip | Put an opponent's awake cat back to sleep |
| Wands | Snails | Counter Catnip ("eat the catnip") |
| Jesters | Laser Pointer | Reveal the top card; Number cards count around the table |

Theme: become "a crazy cat lady" by collecting the most cats/points.

**Goals**: must support real **online multiplayer** (not just local hotseat), with the end goal of deploying to the user's own server as a public demo of "vibe coding" (AI-assisted development).

Origin: the user started this in a claude.ai web chat, then moved to Claude Code/VSCode. That earlier chat history isn't importable — the code in this repo (github.com/drumovski/crazy-cat-lady) is the sole source of truth.

## Development

```bash
npm install
npm run dev      # Vite dev server (the UI)
npm run server   # multiplayer server (needed for online play)
npm run build    # production build
npm run lint     # oxlint
node src/game/engine.test.js   # engine test suite (console.log assertions, not a runner)
node src/game/ai.test.js       # AI policy test suite
```

Local hotseat only needs `npm run dev`. Online multiplayer needs `npm run dev` + `npm run server` together (separate terminals).

## Repo layout

- `src/game/engine.js` — pure game logic (deck, turns, win conditions, sfx event tracking). No UI or networking. Mutates its `game` argument in place and returns it, rather than returning a new object.
- `src/game/engine.test.js` — console.log-assertion test suite (no framework); run with `node`.
- `src/game/ai.js` / `ai.test.js` — AI opponent decision policy, deliberately kept separate from `engine.js` ("who is AI" is a UI-layer concept the engine doesn't know about).
- `src/game/blockTimer.js` — shared constants/validator for the configurable block-response countdown.
- `src/game/timings.js` — the *fixed* (non-player-configurable) timing constants: `AI_THINK_DELAY_MS`/`LASER_REVEAL_DELAY_MS` (ms, imported by both `App.jsx` for local hotseat and `server/rooms.js` for online, so there's one number to change instead of two hand-kept-in-sync copies) and `CARD_FLY_DURATION_S` (seconds — Framer Motion's `transition.duration` expects seconds, not ms, hence the different unit/suffix from the other two; see "Card animations" below).
- `src/sound/sfx.js` — sound-effect playback (see "Sound effects" below).
- `src/components/` — the React UI, shared between local hotseat and online play via `GameBoard`'s `myPlayerId` prop (see below).
- `server/` — Socket.IO server: authoritative game state, named rooms, server-run AI turns.
- `src/multiplayer/socketClient.js` — browser-side Socket.IO client.
- `public/sounds/` — sound effect files (mp3), served statically.
- `public/cards/` — illustrated card artwork (png), served statically (see "UI / design" below).
- `Rules.md` — the plain-English rules, single source of truth for player-facing rules text. Rendered in-app by `src/components/RulesModal.jsx`, which imports it as raw text via Vite's `?raw` import suffix and runs it through a small format-specific markdown-lite parser (not a general parser — it only handles this file's actual patterns: whole-line `**bold**` as headings, numbered/bulleted lists, `>` blockquotes, inline `**bold**`). Deliberately dependency-free rather than pulling in a markdown library for one static file. Opened from `ModeSelect.jsx`'s "Rules" button and from `GameBoard.jsx`'s help popover ("Full Rules" link, next to the existing quick-reference blurb). If you edit `Rules.md`, keep it to the block patterns the parser understands (see `RulesModal.jsx`'s comments) or the new content will render as an unstyled paragraph.

## Game engine details

**Cat roster**: `createCats()` returns 12 specifically-named cats (not generic): 2× Ginger Tom (15pts each), Maine Coon (20), Calico (15), Persian (15), Toyger (10), Ragdoll (10), Bombay (10), Russian Blue (10), Sphynx (5), Siamese (5), Bengal (5). Total 135 points, matching the original Sleeping Queens deck.

- **Sleeping cats are fixed slots, not a queue.** `createSleepingCats()` shuffles the 12 cats once into 12 fixed positions; waking targets a specific slot (`wakeCatAtSlot`), and a cat put back to sleep (`putCatBackToSleep`) always returns to its own home slot. This is deliberate — players should be able to remember and re-target slots, like the physical face-down grid in the original game. Never replace with random/FIFO drawing for player-facing choices.
- **Ginger Tom conflict**: the two Ginger Toms can't both be in one player's collection. If a player would gain the second one (Dog wake, Fish steal, Laser Pointer), it goes back to sleep in its own slot instead (`giveCatToPlayer`).
- **Sphynx bonus wake**: waking the Sphynx lets that player immediately wake one more sleeping cat. Modeled as `game.pendingWakeChoice = { playerId, bonus: true, actorId }`, resolved via `respondToWakeChoice`/`respondToWakeChoiceAsAi`. Chains again if the bonus cat is itself `wakesBonus` (future-proofing; only the Sphynx has this trait today).
- **Special Dog cards**: of the 9 Dog cards, 7 are plain (`variant` 1-7, just a different illustration, identical behavior) and 2 have a real gameplay effect via `dogEffect` instead of `variant` (mutually exclusive fields — see `createDeck`):
  - **Guard Dog** (`dogEffect: "guard"`) — the specific cat it wakes gets `cat.guarded = true` (set in `playDog`, only on that direct wake, never on a chained bonus pick). `playFish`/`playCatnip` both reject targeting a guarded cat (checked engine-side, authoritative); the UI backs this up by excluding guarded cats from being clickable during Fish/Catnip targeting (`PlayerPanel.jsx`) rather than letting the click get rejected. `Card.jsx` renders 4 grey vertical bars (`.card-guard-bars`) over any cat with `guarded: true`, at every size it's shown.
  - **Hot Dog** (`dogEffect: "hotdog"`) — grants a second wake via the exact same `pendingWakeChoice` bonus mechanism the Sphynx uses, set from `playDog` right alongside the Sphynx check (`grantsBonus = sphynxBonus || hotDogBonus`). The two stack if a Hot Dog happens to wake the Sphynx (grants a third). Because AI/local/online turn-taking all already handle `pendingWakeChoice` generically (not caring *why* it's pending), Hot Dog's second wake works for AI players and online play with no changes beyond `playDog` itself.
  - `game.lastMessage` kinds `wokeGuardedCat`/`hotDogWoke` (vs. plain `wokeCat`/`wokeBonusCat`) carry a `bonus` field so `formatLastMessage` can mention "and gets to wake another Cat" only when a bonus is actually granted (e.g. not when Hot Dog's second wake has no sleeping cats left to target).
- **Win condition**: 5 cats OR 50 points (2-3 players), 4 cats OR 40 points (4-5 players) — `checkWinner`/`getWinThresholds`. With 3+ players it's possible for all 12 cats to be distributed with no one crossing the threshold; when `sleepingCats` are all null, `checkWinner` falls back to the points leader (ties: cat count, then lowest player id).
- **Blocking is a real reaction**: playing a Fish/Catnip against a target holding a Seagull/Snail sets `game.pendingAction`, resolved via `respondToPendingAction(game, targetPlayerId, blockCardIndex)` (or `null` to decline). AI always blocks when able (`respondAsAi`, no bluffing). Humans get a configurable response window (see "Block timer" below); if they don't respond in time the UI calls `respondToPendingAction(..., null)`.
- **Laser Pointer reveal is a two-step, timer-driven flip.** `playLaserPointer` only flips the top deck card face-up in place (`game.pendingLaserReveal = { playerId, revealedCard }`) — it does not yet add the card to a hand or start the wake-choice count. `resolveLaserReveal(game)` applies that effect and is called ~2s later so every player gets a beat to see the card before it resolves. This isn't a decision anyone (human or AI) makes, so `validateTurn` blocks all other actions while it's pending, same as `pendingAction`/`pendingWakeChoice`. Local hotseat drives the 2s timer client-side in `App.jsx`; online drives it server-side in `server/rooms.js`'s `scheduleNextStep` (renamed from `scheduleAiIfNeeded` — it now also owns this non-AI automatic step, chaining into AI scheduling afterward). Both timers come from `src/game/timings.js`'s `LASER_REVEAL_DELAY_MS`/`AI_THINK_DELAY_MS` (see "Repo layout") rather than two hand-synced copies.
- **Every card has a stable `id`, separate from its position in any array.** `createDeck()` assigns each draw-deck card an incrementing `id` at creation (`createCats()` already did this for the 12 cats); it never changes as the card moves between deck/hand/discard/reshuffle. This matters because a card's *index* in `player.hand` is not stable — playing/discarding one splices it out and shifts every later card down an index — so any UI code that needs to track "this specific card" across renders (React `key`s, and Framer Motion's `layout`/`AnimatePresence` — see "Card animations" below) must key off `card.id`, never the array index. Engine functions themselves stay index-based (`cardIndex` params) since those are only ever resolved synchronously at the moment of a click, before any array mutation — no need to thread ids through the engine's public API.
  - **Bug, fixed: cat ids must be disjoint from deck card ids.** `createDeck()` and `createCats()` used to assign ids from two independent counters that both start at 0 — a sleeping/collected cat and a deck/hand/discard card could end up with the same numeric `id` purely by chance. Since Framer Motion's `layoutId={`card-${id}`}` (Card.jsx/CardBack.jsx) must be unique across the whole tree at any given moment, and cats render simultaneously alongside deck/hand/discard cards in the same game, a collision made Framer Motion treat two unrelated cards as one shared element and silently drop one of them from rendering — intermittent (only when a currently-visible cat's id happened to match a currently-visible deck card's id) rather than a permanent breakage, which is what made it read as "sometimes the cat cards don't render." Fixed by offsetting cat ids well past the deck's max id (`CAT_ID_OFFSET = 1000` in `engine.js`, deck only ever has 68 cards/ids 0-67). If either roster's size ever changes enough to approach that gap, bump the offset.
- **Dog cards can't be discarded** — `discardCard` rejects `type === "dog"` outright (must be played, not discarded). Enforced engine-side (authoritative for online) and the UI's discard-pile target excludes Dog selections too.
- **Discarding**: single non-Dog card (`discardCard`) or a math set — matching pair or an addition set of Number cards (`isValidMathDiscard`, `discardMathSet`) — both draw replacements.
- **`game.lastMessage`** is structured data (`{ playerId, kind, ...fields }`), not pre-formatted text, specifically so the UI can render current player names and pick correct pronouns at render time rather than baking in stale text. `GameBoard.jsx`'s `formatLastMessage` builds the final string, with an `isSelf` parameter — **always false in local hotseat** (no single "you" when the whole screen is shared and turns keep advancing) and `myPlayerId === message.playerId` in online mode. Any new message kind must default to third-person-safe phrasing; don't hardcode "you/your" unless the render is provably gated to the one player it's about — this exact bug class has recurred twice.

### Block timer (configurable)

`src/game/blockTimer.js` defines `BLOCK_TIMER_MIN`/`MAX` (4-20), `DEFAULT_BLOCK_TIMER_SECONDS` (10), and `isValidBlockTimerSeconds` (accepts an int in range, or `null` = no timer/"Never"). Chosen once by the game creator:
- Local: `SetupScreen.jsx` dropdown → threaded through `App.jsx` state → `GameBoard` prop.
- Online: `OnlineSetup.jsx`'s "Create Room" screen only (joiners inherit it) → `server/rooms.js` sanitizes/clamps it server-side (never trust the client value) → stored on the room → broadcast via `roomState`.
- `GameBoard.jsx`: `null` skips starting the countdown entirely (no overlay, no auto-resolve-unblocked timeout, banner reads "can block at any time").

### Player names (remembered across games)

Typed names survive `backToMenu()`/"New Game" instead of coming back blank — `App.jsx` holds them (`savedPlayerNameInputs` for local's 5-seat array, `savedOnlineName` for online's single field) and deliberately does *not* reset them in `backToMenu`, passing them back down as `initialNames`/`initialName` props the next time `SetupScreen`/`OnlineSetup` mount. Since both components fully unmount between games (conditionally rendered), a plain `useState(initialProp)` correctly re-seeds from the latest saved value each time.
- `SetupScreen.jsx`'s `onStart` callback passes the *raw* per-seat input array (`playerNames`) as a 5th argument, separate from the resolved `finalNames` (which has "Player N" substituted for blanks and AI names filled in) — persisting the raw array means a left-blank seat stays blank next time, rather than "remembering" an auto-generated placeholder as if it had been typed.

### Sound effects

`src/game/engine.js` tags a fresh `game.sfxEvents` array (e.g. `["fish", "dealCard"]`, `["shuffle", "dealCard", "dealCard", ...]`) on every real state-changing action; `GameBoard.jsx` consumes it and calls `playSfxBatch` (`src/sound/sfx.js`), which staggers playback ~150ms apart so bursts (a math discard drawing 3 cards) read as distinct sounds rather than one blob.

- **Reset timing matters**: `game.sfxEvents = []` is set *after* each function's validation checks pass, not unconditionally at the top. This is deliberate — React StrictMode (dev only) double-invokes the same state-updater call, and the second (rejected-by-validation) invocation must not wipe out the sfxEvents the first, real call already recorded. If you add a new mutating action, follow this same placement.
- `createGame` seeds `sfxEvents` with `["shuffle", ...N × "dealCard"]` (initial deal doesn't go through `drawCard`, so it's queued explicitly) — this is what plays on a brand new game.
- `drawCard` pushes `"dealCard"` per card actually drawn; `reshuffleDiscardIntoDeck` pushes `"shuffle"` when it actually reshuffles; `finishTurn` pushes `"win"` (→ `Applause.mp3`) whenever `checkWinner` finds one, appended after whatever else that action already queued (so e.g. a game-winning Dog play plays wake-then-applause, not applause alone). All three use `game.sfxEvents?.push(...)` (optional chaining) since not every caller context initializes the array.
- The block-timer countdown has its own looping "clock tick" sound (`startClockTick`/`stopClockTick` in `sfx.js`, a single persistent `Audio` with `loop = true`, distinct from the one-shot event sounds) — started/stopped by the same `useEffect` that runs the countdown in `GameBoard.jsx`, so it's cut off immediately (even mid-clip) whenever the countdown ends, whether by timeout or an early response.
- `GameBoard.jsx` also guards the sfxEvents-consuming effect with a `useRef` (`playedSfxRef`) storing the last-played array *reference* — needed because StrictMode's dev-only double-invoke of *effects* (separate from the double-invoke of state updaters above) would otherwise play every sound batch twice under `npm run dev`. Verified: production build plays each sound exactly once; without the ref guard, dev build played everything twice.
- Sound files live in `public/sounds/` as `.mp3` (converted from the original `.wav` exports to cut deploy size ~10x — e.g. `Laser Pointer2` went from 824KB to 58KB). No `ffmpeg` is installed as a project dependency; conversions so far used a temporarily-installed `@ffmpeg-installer/ffmpeg` (`npm install --no-save`, removed after).
- **Volume settings**: `src/sound/soundSettings.js` holds two independent persisted (`localStorage`) volume levels (0-1 floats, default 1) — music and sound effects — each its own plain pub-sub channel (`getMusicVolume`/`setMusicVolume`/`subscribeMusicVolume`, and the `Sfx` equivalents), built from one shared `makeVolumeChannel` factory rather than duplicating the pub-sub logic twice. Module-level state, not React context, so non-React code (`sfx.js`, `music.js`) can read it synchronously before playing anything — same pattern as `sfx.js`'s own module-level `audioCache`/`clockAudio`. `playSfx`/`startClockTick` set each `Audio` instance's `.volume` from `getSfxVolume()` (skipping playback entirely at 0); the looping clock tick additionally subscribes to apply a live volume change immediately mid-countdown, stopping outright at 0 (one-shot sounds already in flight aren't retroactively adjusted — not worth tracking every live `Audio` instance for a sub-second ding). `src/components/SoundSettings.jsx` is the UI: a speaker icon button (mirroring `GameBoard.jsx`'s hand-drawn SVG icon style) that toggles a small popover with two `<input type="range">` sliders (Music, Sound Effects); the icon shows "muted" only when both are at 0. Rendered independently on `ModeSelect.jsx` (top-left, absolutely positioned within `.setup-screen`) and in `GameBoard.jsx`'s `board-header` (grouped with the Help icon in `.board-header-left`) — only one is ever mounted at a time, but both read/write the same settings so a change carries over between screens.
- **Background music**: `src/sound/music.js` is a standalone module-level player (not a React component, not tied to any screen) — `startMusic()` is called exactly once, at `App.jsx`'s module scope alongside `preloadCardImages()`, so a single persistent `Audio` element keeps playing across menu → setup → game → New Game without ever restarting. Plays `public/music/Crazy Cat Lady 1.mp3` through `4.mp3` back-to-back in order (advancing via the element's own `ended` event, not `loop`), then wraps back to track 1 — a real sequenced playlist, not independently-looping tracks. The track list is just the `TRACKS` array; `playNextTrack`'s `(trackIndex + 1) % TRACKS.length` advance doesn't hard-code a count, so adding/removing a track (as happened going from 2 to 4) is a one-line change. Browsers block audio-with-sound before any user gesture, so the module-load call is expected to be silently blocked; a `pointerdown`/`keydown` listener on `window` retries once on the first real interaction anywhere (removed after that first attempt — a gesture-triggered `play()` reliably succeeds). Reads/applies `getMusicVolume()`/`subscribeMusicVolume()` from `soundSettings.js`, entirely independent of the sound-effects volume.

## AI opponents

`src/game/ai.js` — pure, engine-agnostic policy. Priority: Dog (free cat, random available slot) > Fish (steal richest opponent's highest-value cat) > Catnip (same targeting) > Laser Pointer > discard (a same-value Number pair via `findMathDiscardPair`; addition-sets are NOT modeled for AI, deliberately). `chooseAiTurn`/`takeAiTurn` apply a decision by calling straight through to the matching engine function. AI names come from a fixed list (`AI_NAMES`: HAL 9000, R2-D2, C-3PO, WALL-E, Skynet, Agent Smith, Ultron, Baymax, Ava, Bishop, Roy Batty, TARS, CASE, T-800), picked without repeats per game via `pickRandomAiName`.

Local mode: `App.jsx` runs a `useEffect` that, whenever the current decision-maker (turn owner, or a pending action/wake-choice target) is AI-controlled, waits `AI_THINK_DELAY_MS` (700ms) then auto-applies the right response. Online mode: the equivalent lives server-side in `server/rooms.js`'s `scheduleNextStep`, chaining automatically through consecutive AI decision-makers (and through the non-AI Laser Pointer reveal delay — see above).

## Online multiplayer

Node.js + Socket.IO (`server/`). Named rooms (creator picks a name, not a random code), not accounts/matchmaking. Server is fully authoritative — it runs `engine.js` itself, and a client can only ever act as the seat its socket is bound to (`server/rooms.js`'s `socketToSeat` map; `playerId` is never taken from client-sent data).

- `server/rooms.js` — in-memory room store (`Map`, keyed by lowercased room name for case-insensitive lookup; `room.roomName` keeps the creator's original casing for display). Creator always gets seat 0; `numAiOpponents` claims the *last* N seats as AI. `createGame` only runs once every human seat is filled (`room.status` starts `"waiting"`, becomes `"playing"`).
- `server/index.js` — Socket.IO wiring: `createRoom`/`joinRoom` (ack callbacks, which now also carry the full current room state — see below) and `gameAction` (fire-and-forget, `{roomName, type, args}`, `type` maps to one engine function via the `ACTIONS` table in `rooms.js`). Broadcasts full `roomState` after every change.
- `src/multiplayer/socketClient.js` — thin client wrapper. Server URL via `VITE_SERVER_URL` (a Vite env var, read at *build* time, not runtime), defaults to `localhost:3001`. Connects with `transports: ["websocket", "polling"]` — deliberately not WebSocket-only, so a hosting proxy that doesn't pass WebSocket upgrades through cleanly (a real risk on shared-hosting Node.js apps) degrades to long-polling instead of failing to connect outright.
- `GameBoard.jsx` is shared between local and online via an optional `myPlayerId` prop: `undefined` → local hotseat (reveal whoever's turn it is, matching shared-screen pass-and-play); a specific seat id → online (always reveal that seat's own hand regardless of whose turn it is, and gate interactivity on `activePlayerId === myPlayerId`).
- **Known race, fixed**: a client joining/creating and immediately filling the last seat could miss the one-time `"playing"` broadcast if it only started listening for `roomState` *after* processing the join/create ack. Fixed by having the ack itself carry the full room state (`roomState(room)` spread into the ack payload in `server/index.js`), so the client can act on it directly instead of waiting for a broadcast that may have already fired. General lesson: don't have a component re-subscribe and wait for the same one-time event its caller already received — forward the payload instead.
- **Known bug class, fixed**: anywhere a value is normalized for lookup (e.g. room name lowercased for the `rooms` Map), every *other* place using the same raw input (like the Socket.IO room/channel to `.join()`) must use the normalized/canonical version too, or it silently diverges. Caught once already in the room-name join handler.
- **Known bug, fixed: duplicate `roomState` delivery caused duplicate sound.** When a room's last human seat fills — room creation with enough AI opponents to fill the rest, or a second human joining — the server runs `createGame` and delivered that fresh state to the just-connected socket via *two* channels: the join/create ack, and the immediate `broadcastRoom` right after it (which still includes that same socket, since it already joined the Socket.IO room). Every Socket.IO delivery independently re-serializes its payload into fresh objects/arrays, and the client's sound-batch dedupe (`GameBoard.jsx`'s `playedSfxRef`, see "Sound effects" above) compares `game.sfxEvents` by reference — so it couldn't tell the ack's copy from the broadcast's copy, and played the same `"shuffle"` (and every deal-card ding) twice, audibly overlapping. Fixed in `server/index.js`: `broadcastRoom(room, excludeSocket)` takes an optional socket to exclude (`excludeSocket.to(room).emit(...)` instead of `io.to(room).emit(...)`), and the `createRoom`/`joinRoom` handlers pass their own `socket` — that socket already has the state via its ack, so it's skipped on this one immediate broadcast, while every other already-connected socket (e.g. the creator, still waiting when a second human fills the room) gets it normally. Later broadcasts (`scheduleNextStep`'s chained ones, `gameAction`'s) are unaffected — they don't have a matching ack to be redundant with.
- No room cleanup/expiry exists — room names are never freed. Not addressed since it wasn't asked for; flag if the user hits "name already in use" friction.

## Deployment

Target: the user's own SiteGround hosting (GrowBig/GoGeek plan — has SiteGround's Site Tools "Node.js App" feature) plus the purchased domain `crazycatladygame.com`. Not yet deployed as of this writing — this documents the intended path.

- **Split across two hosts under one domain**: the static frontend serves from `crazycatladygame.com` (plain static hosting, `public_html`); the Socket.IO server runs as a separate SiteGround Node.js App on a `server.crazycatladygame.com` subdomain. Avoids routing both concerns through one domain/path.
- **Backend**: SiteGround Site Tools → Devs → Node.js App, startup file `server/index.js`. Upload keeping the repo's relative layout intact (`server/` imports from `../src/game/*.js`, so that folder must exist alongside it) — install dependencies via Site Tools' own NPM Install rather than uploading `node_modules`. Needs env var `CLIENT_ORIGIN=https://crazycatladygame.com` (read by `server/index.js`'s CORS config) and SSL enabled on the subdomain (required for `wss://` once the frontend is served over `https`).
- **Frontend**: `VITE_SERVER_URL` must be set at *build* time (Vite bakes it into the bundle, it's not a runtime value) — e.g. `VITE_SERVER_URL=https://server.crazycatladygame.com npm run build` — then upload `dist/`'s contents to `public_html`.
- **Known risk, mitigated**: shared-hosting Node.js apps run behind a proxy layer whose WebSocket-upgrade support isn't guaranteed. `socketClient.js` already allows a long-polling fallback (see above) so this degrades gracefully instead of failing to connect — after deploying, check the browser Network tab to see whether it actually negotiated `websocket` or fell back to `polling`.

## UI / design

A visual redesign (originally based on a reference mockup, since removed from the repo once superseded) has landed across card backs, draw-deck card art, and cat art.

- `src/components/CardBack.jsx` — face-down card rendering, two hand-drawn SVG variants: `"cat"` (teal, paw icon; sleeping-cats grid) and `"deck"` (purple, ball icon; draw pile).
- `src/components/Card.jsx` — face-up cards. All card types (including cats now) use illustrated PNG art from `public/cards/` (`getCardImageSrc`, keyed by `card.type`/`card.value`/`card.variant`, `card.dogEffect` for Guard Dog/Hot Dog, or `getCatImageSrc` for cats — see below) with `.card-has-art`/`.card-art` in `App.css` dropping the CSS-drawn frame so the image's own border shows through. The non-illustrated emoji+rank+label shell is now a dead-code fallback (`getCardImageSrc`'s `default: return null`) kept only for robustness against an unrecognized `card.type`, not something any real card currently hits. Guarded cats additionally render `.card-guard-bars` (4 grey vertical bars, `inset: 6%` + `justify-content: space-between` with fixed-width spans — not `flex: 1`, which fills nearly the whole card as solid blocks instead of thin bars with visible gaps) on top.
- **Cat art has no point value baked in** (unlike every other card type's art) — `Card.jsx` overlays it itself via `.card-rank-cat` (reuses `.card-rank`'s existing top-left positioning, just swaps the font). It also gives itself a small white circular/pill backdrop (`border-radius: 999px`, sized in `em` so it scales with `.card-rank`'s own per-size font-size automatically — a true circle for single-digit values, a rounded pill rather than a squashed oval for two-digit ones like Maine Coon's 20) since plain text sometimes sat right on top of busy illustrations, especially at `mini` size in opponents' collected-cats rows, and got hard to read. `getCatImageSrc` is a name→filename lookup with two irregularities worth knowing about: **"Maine Coon" maps to the file `Main Coon.png`** (a typo in the actual filename on disk, deliberately matched rather than "fixed" — if the file's ever renamed, update this one function), and **Ginger Tom needs `card.variant` (1 or 2)** to pick between its two distinct illustrations (`Ginger1.png`/`Ginger2.png`) since both cats share the same name — `createCats()` sets this the same way `createDeck()` sets Dog's `variant`. `preloadCardImages.js`'s file list must stay in sync with `getCatImageSrc` (and `getCardImageSrc` generally) if the art set changes.
- **The point-value font (Irish Grover) is self-hosted, not a Google Fonts CDN link** like Figtree/Caprasimo — `public/fonts/IrishGrover-Regular.ttf` (supplied as a local file, not requested as a web font), loaded via a `@font-face` in `index.css` and referenced through the `--card-value-font` custom property (`.card-rank-cat` is the only current consumer). Only one weight exists, so `.card-rank-cat` explicitly sets `font-weight: 400` — relies on `index.css`'s global `font-synthesis: none` not faking a bold that isn't there, but states it explicitly rather than leaning on that silently.
- **The board header's "Crazy Cat Lady" title (Henny Penny) is self-hosted the same way** — `public/fonts/HennyPenny-Regular.ttf`, its own `@font-face` in `index.css`, referenced through a separate `--title-font` custom property (kept distinct from `--card-value-font` since they're two unrelated fonts that happen to share the same "self-hosted, one weight" setup). `GameBoard.jsx` renders it as a plain `<h1 className="board-title">Crazy Cat Lady</h1>` — this replaced the old `.room-pill` treatment (a cream pill background + `CatEarIcon` SVG, both deleted) with bare decorative text sitting directly on the green felt, matching how `.your-cats-label`/`.pile-label` already do it. Because `.room-pill` and `.win-pill` (the separate "Win condition: ..." banner) used to share one CSS rule, removing `.room-pill` required rewriting `.win-pill` in `App.css` as a fully self-contained rule rather than leaving it partially orphaned.
- **Illustrated-card alt-text flash, fixed**: before an `<img>` finishes loading, the browser renders its `alt` text (the card type) in plain inherited-color text — a real ~1s glitch on a cold load given each card PNG is ~60-100KB. Fixed two ways: `.card-art { color: transparent; font-size: 0; }` in `App.css` hides that fallback outright (a loading card is a blank box, not a stray text readout), and `src/components/preloadCardImages.js`'s `preloadCardImages()` (called once at module scope in `App.jsx`, so it fires as soon as the app loads) warms the browser's image cache for the whole deck ahead of the first hand ever rendering. Its file-path list must stay in sync with `getCardImageSrc` if the art set changes.
- **`GameBoard.jsx`'s `isBoardBusy` is the single gate for "don't accept input right now"** — still just `Boolean(game.pendingLaserReveal)`, feeding into `canInteract` alongside the existing turn/seat checks. Deliberately *not* extended to also gate on a card animation being mid-flight (see "Card animations" below) even though that was the original plan for this variable — the animations are cosmetic and don't block game-state correctness (`validateTurn`/`pendingAction` guards already prevent double-applying an action regardless of whether its animation finished), so adding an input-blocking dependency on animation timing would only be extra risk for no real correctness benefit. Still the one obvious place to OR in a future "don't accept input" condition if a real need for one shows up.
- **Emoji were pulled from AI names and the message log**, not everywhere — `PlayerPanel.jsx` no longer suffixes an AI opponent's name with 🤖 (the `isAi` prop was removed along with it, since nothing else used it), and `GameBoard.jsx`'s message log no longer prefixes each row with 🐱. Left alone deliberately: the menu title, the win-screen banner, and `Card.jsx`'s unillustrated-card fallback — only the two flagged spots were touched, not a blanket "no emoji" sweep.
- **`PlayerPanel.jsx`'s name and score sit side by side** (`.player-panel-header`, `flex; justify-content: space-between`) instead of stacked — stacking them ate into the vertical space available for the collected-cats row below, most noticeable as wasted space right when a player's first cat appeared.

### Card animations (Framer Motion)

Cards genuinely **fly** between zones (hand → discard, sleeping slot → cats panel, target's cats panel → attacker's), not just fade-out-here/fade-in-there — this needs `layoutId`, not the plain `layout` prop. First attempt used `layout`, which only smooths *reflow within the same list*; two different `.map()` calls in two different components are two unrelated mounts, and `layout` alone can't connect them. `layoutId` is what tells Framer Motion "these are the same object" so it computes the FLIP between their positions/sizes automatically, wherever in the tree they are. Verified by sampling an animating card's `getBoundingClientRect()` every 40ms mid-transition — position interpolates smoothly frame to frame, not an instant jump.
- **Every `Card` and every cat-representing `CardBack` gets `layoutId={`card-${id}`}`**, using the same id scheme (`card-<id>`) so a sleeping cat's face-down `CardBack` and its eventual face-up `Card` are recognized as the same object — waking a cat flies *and* flips it from the sleeping grid into the cats panel. The draw pile's `CardBack` is the one exception: no `layoutId`, since it's face-down/anonymous with no specific-card identity to share (there's nothing sensible to morph *from*).
- `Card`/`CardBack` also carry `initial`/`animate`/`exit` variants (default: pop in/out) for the *local* presence animation — this is what plays when a card appears/disappears with no matching `layoutId` partner in the same commit (rare in practice, since almost everything that leaves one zone lands in another in the same state update) and governs opacity/scale on top of whatever position the layout projection computes. A `variants` prop lets callers override the default in-place pop — `GameBoard.jsx`'s hand fan passes `HAND_CARD_VARIANTS` so cards without a flying partner (there usually is one, but this is the fallback) fall in/out from roughly where the draw pile sits.
- **Exit animations require `<AnimatePresence>` around the `.map()`** — without it, React unmounts a removed card instantly, with no time for Framer Motion to animate anything, `layoutId` included. Every list of `Card`s/`CardBack`s that can shrink is wrapped in one (`GameBoard.jsx`'s hand fan, `.your-cats-row`, and the discard pile's single-card slot; `PlayerPanel.jsx`'s `.player-cats`) — **except `SleepingCatsGrid.jsx`, deliberately.**
- **`SleepingCatsGrid.jsx` is NOT wrapped in `AnimatePresence`, and this matters.** It's a `display: grid` with a fixed 2-column auto-placement — first attempt *did* wrap it, and `AnimatePresence` keeping an exiting slot mounted alongside its already-rendered replacement briefly creates a 7th child, which the grid's auto-placement algorithm reflows around: the whole grid visibly cascades/shifts for a moment, not just the one slot changing (caught this live in a screenshot — a diagonal trail of every card-back in the grid, not a clean single-slot transition). Fixed by simply removing `AnimatePresence` there. This turns out not to cost anything: the flying effect comes from the *destination* element (the woken cat's `Card` elsewhere on the board) animating in from the slot's last known position via the shared `layoutId` — that mechanism doesn't need the source element to stay mounted after it's gone, only `AnimatePresence`-driven local exit fades do. If you're tempted to re-add it here, don't — reach for explicit `grid-row`/`grid-column` placement per slot first, so a transient extra child can't shift the others.
- **The discard pile's top card is keyed by `card.id`** (`<Card key={topDiscard.id} ...>`), not left keyed by "whatever's rendered in this DOM slot" — without an explicit key tied to the card's identity, React would just update the existing element's props when a new card lands on the pile, and `initial` only plays on a genuine mount, not a prop update, so the pop-in wouldn't replay for each new discard.
- **The `.card-selected`/`.card-eligible` "lift" moved from a CSS `transform` to Framer Motion's `animate` prop** (a `y` offset computed in `Card.jsx` from the `selected`/`eligible` props, merged into `variants.animate`). This is a hard requirement, not a style preference: Framer Motion sets `transform` via inline styles every frame, and inline styles always beat a stylesheet rule on the same property — a `.card-selected { transform: translateY(-14px) }` CSS rule would just get silently overridden. For the same reason, `.card`'s CSS `transition` no longer includes `transform` (only `box-shadow`) — a CSS transition fighting Framer Motion's own per-frame transform updates on the same property causes jank.
- **`src/components/MenuFrame.jsx`** — shared wrapper for every pre-game screen (`ModeSelect`, and all four of `OnlineSetup`'s screens: choose/create/join/waiting): a `.menu-title` heading, the `public/Load Screen no Text.webp` hero art beneath it, `SoundSettings`, and a narrower centered `.menu-content` column for the actual buttons/fields. Extracted here specifically because five separate render paths needed the identical structure. `.menu-screen`'s own max-width (`clamp(520px, ..., 900px)`) is deliberately wider than `.menu-content`'s (`clamp(420px, ..., 520px)`, matching the original `.setup-screen`) — the hero image is allowed to grow bigger than the button column beneath it. No border/shadow on the image itself; it's meant to sit directly on the page. `SetupScreen.jsx` (local hotseat's own player-count/name/AI setup) still uses the plain `.setup-screen` class directly, not `MenuFrame` — it was never asked to get the hero treatment, only the pre-game/online screens were.
  - **The hero art is textless** (`public/Load Screen no Text.webp`, replacing an earlier version that had "Crazy Cat Lady" painted into it) — the title is real text (`.menu-title`) rendered above the image instead, in the same self-hosted Henny Penny font as `GameBoard.jsx`'s in-game `.board-title` (both reference the shared `--title-font` custom property), large (`clamp(40px, ..., 72px)`) and black, distinct from the felt-table version which is small/white/shadowed to sit on a dark background.
  - **Converted PNG → WebP to cut deploy weight**, same motivation as the sound-effects mp3 conversion: the original PNG was ~2.2MB; `sharp` (`npm install --no-save`, removed after, same temporary-tool pattern as the earlier `@ffmpeg-installer/ffmpeg` use) re-encoded it to WebP at quality 85, ~314KB (~86% smaller) with no visible quality loss at the sizes it's actually displayed — verified by comparing before/after screenshots pixel-for-pixel. The source PNG wasn't kept in the repo (no precedent for keeping pre-conversion sources — the original sound `.wav` files weren't kept either).
- **Fluid scaling, not a breakpoint.** `App.css` originally had a single `@media (min-width: 768px)` block jumping every size straight from mobile to desktop with nothing in between (identical at 400px and 767px, then an abrupt jump). Replaced with `clamp(min, calc(intercept + coeff*vw), max)` on essentially every font-size/padding/gap/width in the file, so sizing scales continuously with viewport width instead. All of them share the same interpolation range (360px viewport → 900px, chosen since `.game-board`'s own 960px max-width caps it there anyway) so everything scales together proportionally rather than at uneven rates; min/max are exactly the old mobile-base/desktop-media-query values, so the look at both ends is unchanged — only the transition between them is new. If you add a new size-varying rule, compute its clamp() the same way (min = old mobile value, max = old desktop value, same 360→900 range) rather than reintroducing a hard breakpoint.
  - **Exception: `.game-board` goes edge-to-edge below 600px, via a real `@media` breakpoint, not a clamp().** `#root`'s horizontal padding is a flat `16px` (unlike its fluid top/bottom padding) — needed elsewhere, since `.setup-screen`/`.menu-content` have no horizontal padding of their own and rely on it, so it can't just be zeroed globally. At small phone widths the felt should still run flush to the screen edge, so `.game-board` cancels that 16px out locally with a matching negative margin + `width: calc(100% + 32px)`. This is a discrete layout switch (edge-to-edge or not) rather than a continuously-scaling size, so a hard breakpoint is the right tool here, not the clamp() pattern above.
- **Fixed containers with dynamic content must not shift the layout below them.** Several spots reserved a min-height that didn't actually match their real (populated) content's size, so the first time real content appeared, the container visibly grew and shoved everything below it down — jarring since it kept happening: the *first* time, not a one-time settle. Fixed with a shared-measurement approach rather than more independently-guessed numbers:
  - `--card-w-mini`/`-board`/`-hand` and their `--card-h-*` derivatives (`calc(width * 7 / 5)`, matching `.card`'s `aspect-ratio: 5/7`) are custom properties in `index.css`, used by both `.card-size-*` (App.css) and every container that needs to reserve exact card-shaped space — one source of truth instead of two numbers that can drift apart.
  - `.player-cats`/`.mini-cat` (opponents' collected cats) and `.your-cats-row` (your own) reserve full card+label height up front via these variables — including reserving `--mini-cat-label-h` for a *2-line* cat name, not 1: only reserving 1 line meant whichever specific cats happened to have a wrap-eligible name (e.g. "Russian Blue") made their row taller than a short-named one (e.g. "Bengal"), so the panel wobbled as cats were collected/stolen instead of settling once.
  - The message log (`GameBoard.jsx`) always renders all 3 row slots now — hidden-but-height-reserving placeholders (`.message-log-row-hidden`, `visibility: hidden`) for slots with no message yet, "No moves yet." in slot 0 — instead of rendering 0-3 rows based on `messageHistory.length`, which used to visibly grow the log across the first 3 actions of every game.
  - **The discard pile's card-swap crossfade needed a different technique than the hand fan's.** Both have an old card exiting while a new one enters at once; the hand fan handles this with `<AnimatePresence mode="popLayout">` (pulls the exiting item out of flow so siblings don't wait for its exit to finish). The same fix on the discard pile's `AnimatePresence` did *not* work — confirmed via `getComputedStyle(el).position` sampled on both cards mid-transition, both stayed `relative`, never `absolute` — because the exiting discard card is simultaneously mid a *different*, cross-tree `layoutId` flight (from wherever it was originally played), which fights popLayout's own exit-repositioning logic. Fixed instead with a CSS-only technique that sidesteps Framer Motion's internals entirely: `.discard-pile-slot` (fixed size, `position: relative`) wraps the `AnimatePresence`, and every child (`.discard-pile-slot > *`) gets `position: absolute; inset: 0`, so the exiting and entering card overlap in place instead of stacking in flow — the slot's size can never depend on how many cards happen to be mounted mid-crossfade. Prefer this pattern over `popLayout` for any future single-slot card swap (as opposed to a genuine shrinking/growing list) that also participates in a cross-tree `layoutId` flight.
- Known CSS gotcha (fixed once, watch for recurrence): don't dim a card via the generic `.card:disabled { opacity }` rule if that same component is *also* used somewhere it should stay fully bright/opaque (e.g. the "Your Cats" display panel, which is always `disabled` since it's never clickable) — scope the override to the specific container instead (`.your-cats-row .card:disabled { opacity: 1; }`). Same idea for overlapping/fanned cards (`.hand-fan`): darken via `filter: brightness()` rather than `opacity`, since `opacity` on overlapping elements lets the one underneath show through the gap.

## Standing lessons (apply to future work)

1. **Structured data out of the engine, formatting in the UI.** `game.lastMessage`'s `kind` + fields pattern exists so the UI can render current player names / correct pronouns at render time. Don't have the engine emit pre-formatted "Player N ..." strings.
2. **"You/your" phrasing bug class.** Any player-facing text derived from tagged message state must only use second-person phrasing when the render is provably gated to the one player it's about (true in online mode, generally *not* true in local hotseat's shared screen). Default to third-person-safe phrasing otherwise.
3. **Mutate-in-place engine + React StrictMode.** Engine functions mutate their `game` argument and return it; `App.jsx`'s `applyAction` relies on this. StrictMode (dev only) double-invokes the state-updater, so every action currently runs twice per click in `npm run dev` — harmless so far because validation guards (`validateTurn`, `pendingAction`/`pendingWakeChoice` checks) reject the redundant second call, since the first call already mutated the field being checked. This is incidental protection, not designed-in — a new action without an equivalent guard could silently double-apply on a StrictMode double-invoke. Root-cause fix if it ever bites: `structuredClone(prevGame)` before passing into an engine function inside `applyAction`.
4. **Normalize once, use everywhere.** If a value is normalized for lookup purposes (case, whitespace), every other consumer of the same raw input must use the canonical version too.
5. **Server-side validation is authoritative; never trust client-sent values for anything that matters** (playerId, block timer seconds, etc.) — sanitize/clamp server-side even if the UI already prevents bad input.
6. **A reserved size must match the real *populated* content, worst case included, not a guessed number.** A container's `min-height` that's smaller than its actual content once real data shows up just delays the layout shift rather than preventing it — and if that "real data" varies (a cat name that sometimes wraps to 2 lines, a message log that fills in over several turns), reserve for the *worst* case, not the common one, or the shift still happens intermittently. See "Fixed containers with dynamic content..." under UI / design.
7. **Two elements re-serialized from the same source aren't the same object.** Anything compared by reference for dedupe (a Framer Motion ref-guard, a socket broadcast) breaks the moment the value crosses a serialization boundary (React StrictMode double-invoke is fine — the ref survives; a network round-trip, or two independent round-trips of the *same* logical update, is not). See the online `roomState`/sfx double-play bug under Online multiplayer.
